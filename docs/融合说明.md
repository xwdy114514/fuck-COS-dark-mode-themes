# 融合说明：ThemeLock 2.2-rc5 + MCTGA 0.2.1 → MCTGA 0.3.0

## 一、为什么能合

两个项目的技术栈不冲突，各自负责主题生命周期的不同阶段：

- **MCTGA（LSPosed 模块）**：解决“装了主题但深色模式看不到”。运行在目标应用进程里，改的是
  `OplusThemeResourcesPackage` / `OplusThemeZipFile` / `Resources`，以及 13 个应用的窗口背景。
- **ThemeLock（Shizuku 工具）**：解决“主题过几个小时被恢复默认”。运行在 shell 身份，改的是
  主题商店的 `files/Themes`（空文件替换 + `pm suspend`）。
- 二者唯一的交叉点是 `/data/theme`：MCTGA 需要它存在，ThemeLock 不碰它。所以可以做成一个应用：
  同一套界面里，先装主题、再生效、最后锁定。

## 二、身份分工

| 动作 | 身份 | 原因 |
|---|---|---|
| 写 `/data/theme/<包名>`、`chown 10303` | Root（`su -c`） | `/data/theme` 属主是 uid 10311，普通应用不可写 |
| `am force-stop` 一串应用、`killall com.android.systemui` | Root | 需要系统权限 |
| 读 `Themes` 状态（`inspect`） | 优先 Shizuku，其次 Root | 两种身份都能读，Shizuku 更稳（root 读 FUSE 受限时回退） |
| 锁定 / 解锁（空文件 + `pm suspend`） | **只能 Shizuku** | `ThemeEngine.guard()` 要求 `id -u = 2000`，root 的 0 会被拒 |

因此本应用同时声明了 Shizuku provider，并且用旧版广播兜底拿 binder（ColorOS 14 上 provider 不会回调）。

## 三、代码来源

| 文件 | 来源 | 改动 |
|---|---|---|
| `Hook.java` | MCTGA 0.2.1 | **未改动**（仅保持包名 `xwdy.deepseek.test`） |
| `arrays.xml` / `bg_day.png` / `bg_night.png` | MCTGA 0.2.1 | 原样 |
| `ThemeEngine.java` | ThemeLock 2.2-rc5 | 只改 package |
| `ShellRunner.java` | ThemeLock 2.2-rc5 | 只改 package（有界执行、`exitValue` 轮询规避 “process hasn't exited”） |
| `ShizukuBridge.java` | 由 ThemeLock `Backend` 抽出 | 只留授权状态 + `Shizuku.newProcess` 反射通道 |
| `RootShell.java` | 新写 | `su -c` 通道，复用 `ShellRunner` 的超时与限流 |
| `MainActivity.java` | 重写 | 深色 UI，融合状态卡 + 6 个动作 + 高级选项 |

它的 `WORKSPACE` 指向 `AI_Agent_workspace/`，与本工作空间约定冲突，且报告对象是 ThemeLock 单项目。
需要的话可以在下一版按新工作空间重写一版诊断导出。

## 五、构建链变化

MCTGA 原来的 `build2.sh` 用 `javac -bootclasspath android.jar`，只能编匿名内部类；
ThemeLock 的 `ShellRunner.java` 用了 lambda（`FutureTask<>(() -> {...})`），在那种模式下会报
`Unable to find method metafactory`。所以融合版改成 ThemeLock 的写法：

```sh
javac --release 8 -classpath "android.jar:XposedBridgeAPI-82.jar:shizuku-*.jar"
d8 --release --lib android.jar --min-api 26 shizuku-*.jar <所有 class>
```

d8 负责 lambda 的 desugar，`--min-api 26` 下没有问题。

`assets/xposed_init` 与两张底图沿用 0.2.1 的打包方式：底图放 **APK 根目录**
（`Hook.loadBg` 用 `Hook.class.getClassLoader().getResourceAsStream("bg_night.png")` 读取，
不能放 `assets/`，因为 Hook 运行在目标应用进程，拿不到模块的 assets）。

## 六、已知风险

1. **装完必须重启目标应用**：Hook 的代码跟着进程走，`一键生效` 就是干这个。
2. **Shizuku 未授权时锁定按钮不可用**：会弹引导。首次安装后需要在 Shizuku 里给 MCTGA 授权。
3. **更新 APK 后 Shizuku 授权**：uid 不变的话授权保留；若被清，重新点一次授权。
4. **不要卸载主题商店**：会触发基础服务恢复默认主题（两项目共同的坑）。
5. **换主题前必须解锁**：`Themes` 是空文件时商店导入功能失效。
6. **`pm install` 不能读 `/storage`**：必须用 `install.sh`（先复制到 `/data/local/tmp`）。

### 环境检测（EnvCheck.java）

一次 root 探测三件事，给出四档结论：

```sh
id -u                          # 有没有 Root
pidof lspd                     # LSPosed 守护进程在不在
ls /data/theme | wc -l         # 有没有主题包
unzip -l /data/theme/<包> | grep -c drawable-night   # 有没有夜间资源
```

| 结论 | 条件 |
|---|---|
| 可用 | Root 可用 + lspd 运行 + 至少一个主题包含 `drawable-night` |
| 有限 | 主题在，但一个夜间资源都没有（深色下看不出变化） |
| 待准备 | `/data/theme` 里没有主题 |
| 不可用 | 没有 Root，或 lspd 没运行 |

本机实测：`Root 可用 / lspd 运行中 / 37 个主题包 / com.android.settings 有 21 项 drawable-night` → **可用**。

### 开关实现（为什么不用 XSharedPreferences）

第一版试过 `XSharedPreferences("cfg")` 读模块自己的 prefs，实测**读不到**（被 catch 后回退默认 true），
因为模块 prefs 在 CE 存储、`rw-rw----`，目标进程（别的 uid）没有读权限，而 targetSdk 35 又不能建
`MODE_WORLD_READABLE`。改成 **Settings.Global**：

- 写：主界面开关 → `su -c "settings put global mctga_dark_attach 0/1"`（要 Root）
- 读：Hook 用 `ActivityThread.currentActivityThread().getSystemContext().getContentResolver()`
  读 `Settings.Global.getInt(cr, "mctga_dark_attach", 1)`，读失败就回退 `true`

实测日志（本机）：

```
CosNightTheme: dark attach = false
CosNightTheme: dark attach disabled, skip pkg=com.android.settings
```

表示开关关掉后 Hook 完全不挂，目标进程就是原厂逻辑；设回 1 后恢复 `loaded pkg=...`。

> 注意：开关是进程启动时读的，改完必须重启目标应用（「一键生效」就是干这个）。

## 九、0.3.3–0.3.7：接 Sui、加解冻/冻结

### 现在的权限真相（本机实测）

| 通道 | 身份 | 能做什么 | 不能做什么 |
|---|---|---|---|
| Sui（Zygisk v13.5.4.3，走 Shizuku API） | shell `uid 2000` | `pm suspend` / `pm unsuspend` / `pm enable`、`am`、`dumpsys` 大部分 | 读 `/storage/emulated/0/Android/data`（inspect 返回 `STATE:INACCESSIBLE`） |
| Root（`su -c`） | — | — | **不可用**：Sui 接管后，app 进程里 `exec("su")` 直接 `ENOENT`，`/system/bin/su` 在挂载命名空间里看不见 |

所以当前这台机器上：

- **解冻 / 冻结主题商店**：可用（纯 `pm` 操作）——实测 `suspended=true` → 点一次「解冻主题商店」→ `suspended=false`
- **锁定 / 解锁（空文件替换）**：不可用，需要能读写 `Android/data` 的身份（无线调试/ADB 启动的 Shizuku，或真正的 Root）。点按钮会直接弹说明，不会去执行半套命令
- **安装 .theme / 一键生效**：不可用（要写 `/data/theme`、`killall systemui`），UI 里 Root 显示「不可用（su 没返回 0）」

### 代码改动

1. `ThemeEngine`：
   - `lock/unlock(pkg, allowRoot)`：守卫允许 `uid 0` 或 `2000`（Sui 给 root 时也能用）
   - 新增 `unsuspend(pkg)` / `suspend(pkg)`：只动 `pm suspend/unsuspend/enable`，不碰 `Themes` 文件
2. `MainActivity`：
   - 主界面新增「解冻主题商店（unsuspend）」，高级里新增「冻结主题商店（suspend）」
   - 状态卡新增「商店状态」「权限通道」「Sui」三行；通道读不到目录时标 `· Android/data 不可读`
   - 挂起状态改用 `PackageManager.isPackageSuspended()`（`dumpsys` 在 Sui shell 下不可靠）
   - `changeTheme` 前置检查：目录读不了就弹说明，不执行
3. `RootShell`：按 `/system/bin/su`、`/debug_ramdisk/su`、`/sbin/su`、`su` 逐个尝试（本机全部 ENOENT，保留以便 Sui 不再接管时自动恢复）

### 想恢复 Root 的两个办法（任选）

1. 在 Sui 里给 MCTGA 授予 root（如果这个 fork 的配置支持），或临时把 MCTGA 从 Sui 注入名单移除；
2. 关掉 Sui 模块，用 KernelSU 自己的 `su`（本机 allowlist 里已有 `xwdy.deepseek.test`，uid 10448）。

## 十一、写入 /data/theme 的开机风险与防护（0.5.1 起）

用户明确要求牢记：**向 `/data/theme` 写入文件可能导致手机无法开机**。它不是普通缓存目录，主题引擎在启动阶段就会读它，写坏一个包就可能在开机时崩。

因此安装流程被收紧成这样：

1. 点「选择并安装 .theme」先弹**风险确认**（写清风险 + 本工具会做的保护），默认按钮是「取消」
2. 只取 `.theme` 里的 `com.*` 成员；`wallpaper`、`lockscreen/`、`picture/`、`icons`、`themeInfo.xml` 一律不碰
3. 先解压到 `/data/local/tmp/eta_import`，逐个 `unzip -t`；任一坏包立刻 `FAIL:BAD_ZIP:<包名>` 退出，**一个字节都不写**
4. 空间检查：剩余空间 < 解压体积 ×2 就停（`FAIL:NO_SPACE`）
5. 覆盖前把将被替换的原文件 `cp -p` 备份到 `/data/local/tmp/mctga_theme_backup/<yyyyMMdd-HHmmss>/`
6. 写入按 `.tmp` → `chown 10303:10303` → `chmod 0666` → `mv` 原子替换
7. `/data/theme` 若被 ThemeLock 的 `chattr +i` 保护，临时 `-i`，结束后恢复
8. 高级里新增「回滚上一次安装」：把最新备份目录里的文件按同样方式原子写回

本机实测（v7 主题，文件与 /data/theme 完全一致）：

```
IMMUTABLE_BEFORE:0
VALID:16
BACKUP:/data/local/tmp/mctga_theme_backup/smoketest
INSTALLED:0
SKIPPED:16
DONE
```

因为没有差异，实际没有写入任何文件。这也就是“默认不动数据”的行为。

## 十二、无 Root 时的界面规则（0.5.4-beta / versionCode 73）

用户要求：没有 Root 就不要显示安装选项，或者想办法无 Root 导入。当前实现是前者 + 把动作交给主题商店：

- `rootReady == false` 时
  - 「选择并安装 .theme」**隐藏**（避免按了必然失败）
  - 「一键生效」**隐藏**（要 `killall systemui`、写 `/data/theme`）
  - 改显示「打开文件管理导入 .theme」＋一行说明：安装与一键生效已隐藏，导入只能在文件管理里点 .theme（免费试用），锁定/解冻仍可用
- `rootReady == true` 时反过来：安装/一键生效显示，文件管理按钮隐藏

**用户明确规则：导入主题只能用文件管理**（文件管理 → 找到 .theme → 点击 → 免费试用），不能用主题商店的导入入口。所以无 Root 时给的是「打开文件管理导入 .theme」，帮助文案第 1 步、安装前风险提示都已改成文件管理路径。

为什么无 Root 真的导不了：`/data/theme` 属主是 uid 10311（主题引擎），文件权限 0666 且目录 0777，但 SELinux 类型是 `oem_theme_data_file`，只有主题引擎/系统/root 域能写；Sui 给的 shell（uid 2000，`u:r:ksu:s0`）没有写权限，Shizuku 的 shell 同样没有。所以无 Root 时唯一合法的写入者就是主题商店自己——把 `.theme` 交给商店导入，写入由它完成。

## 十三、0.5.4-beta（versionCode 76）：锁定幂等 + 目录保护

用户实测：状态卡已经显示「已锁定（空文件）」，再点「锁定主题」弹「锁定未完成 / FAIL:PLACEHOLDER_CREATE」，
shell 原文 `can't create .../Themes: File exists`。

原因：`Themes` 已是 0 字节占位文件，`(set -C; : > "$T")` 在 noclobber 下不允许覆盖已存在的文件，
于是把「已经锁好」当成失败。修法：

- `empty` 成立时直接走「已锁定」分支：补一次 `pm suspend` → 校验 `suspended=true` → `RESULT:ALREADY_LOCKED` → `exit 0`，一个字节都不写
- `Themes` 若是目录，不再 `rm -rf`，整目录 `mv` 到 `<files>/.Themes.lockdir-<时间戳>`；解锁时按最新一份还原并输出 `INFO:DIR_RESTORED`
- `hintFor()` 增加 `PLACEHOLDER_CREATE` / `EXISTING_FILE` / `BACKUP_FAILED` / `RESTORE_FAILED` 的中文说明
- 成功提示区分 `RESULT:ALREADY_LOCKED`（「主题已锁定（原本就是锁定状态）」）和真正新锁定

本机构建工具链与 `build.sh` 的 `jar -C` 改法见 `交接文档.md` 第 9 节。

## 十四、0.5.4-beta（versionCode 77）：解冻仍然“已挂起” + 按钮排版

### 解冻失败的真正原因

`dumpsys package com.heytap.themestore` 显示同一个包有两条挂起记录：

```
suspendingPackage=<0>root
suspendingPackage=<0>com.android.shell
```

ColorOS 允许不同调用者各自挂起同一个包；`pm unsuspend` 只清调用者自己那条。
本工具用 root 挂起、旧 ThemeLock 用 shell 挂起，于是解冻只清掉一半，`suspended` 仍为 true，
界面就报「挂起状态未确认」。

`suspend()` / `unsuspend()` / `lock()` 现在双身份执行（root 时再补一次
`su 2000 -c "pm …"`），以 `suspended=false` 为成功判据，清不干净会输出 `LEFT:<条数>`。
实测两条记录 → 一次解冻后 0 条，`RESULT:UNSUSPENDED`。

### 按钮排版

`button()` 自带的 LayoutParams 没有外边距，`root.addView()` 直接排列时按钮会贴在一起。
新增 `addBtn()` 统一补 10dp 上边距，`action()` / `member()` / 直加的按钮全部走它；
操作区改成三组两列（锁定/解锁、解冻/冻结、文件管理/刷新），列距 12dp、行高 48dp，

## 十五、0.5.4-beta（versionCode 78）：风险确认对话框不出现

用户点「选择并安装 .theme」→ 选完文件返回后只看到「请在前台确认风险后再安装」的 toast，
不知道指的是什么风险。

原因是 `onActivityResult()` 早于 `onResume()` 执行，`canShowDialog()` 里的 `foreground`
这时还是 false，于是走进了 toast 分支。现在用 `pendingInstallRisk` 记住意图，在 `onResume()`
里 `post` 一次 `installTheme()`，界面真正回到前台后再弹风险对话框；安装按钮下面也固定显示一行
风险说明（无 Root 时随按钮一起隐藏），不再让用户猜。

风险本身：`/data/theme` 是主题引擎开机阶段读取的目录，写入不完整 / 不兼容的包可能导致开机异常。
工具侧的防护见 `交接文档.md` 第 11 节；更稳的路径仍是文件管理里点 `.theme` → 免费试用，让商店写入。

## 十六、0.5.4-beta（versionCode 79）：把 .theme 交给主题商店，而不是自己写 /data/theme

用户不想让模块写 `/data/theme`。ColorOS 文件管理点 `.theme` 时并不是自己写盘，而是发 intent 让商店
打开详情页；`dexdump` 反编译 `com.coloros.filemanager` 的 `OpenFileFactory` 得到：

- 新商店：`action=com.oplus.themestore.action.PREVIEW_THEME`，`extra=oplus_preview_theme_path`（绝对路径）
- 老商店：`oppo.intent.action.OPPO_PREVIEW_THEME` / `android.intent.action.OPPO_PREVIEW_THEME`，
  `extra=oppo_preview_theme_path`

商店侧对应的 Activity 是 `com.heytap.themestore/com.nearme.themespace.activities.ThemeDetailActivity`
（`dumpsys package` 里声明了该 action）。

所以现在的「选择 .theme 交给主题商店」= 复制到 `Download/MCTGA/` + 发上面的 intent，由商店显示
详情页并自己写 `/data/theme`；原来的写盘流程降级到「高级 → 手动写入 /data/theme（高风险，不推荐）」，
风险确认仍然保留。

## 十七、0.5.4-beta（versionCode 80）：详情页空白 ≠ intent 失败

拿用户自己的 133 MB 主题实测：`PREVIEW_THEME` 带 `oplus_preview_theme_path` /
`oppo_preview_theme_path` 指向 `Download/MCTGA/` 里的副本，商店详情页要 **6–8 秒**才渲染出
标题和「免费试用 / 购买」；加载期间就是空白 + 「评论 / 收藏」。所以之前看到的“没反应”是加载中。

同时修了文件名清洗：原来用白名单正则，中文被替换成下划线；改成只替换路径非法字符。
已存在同字节数的目标文件时跳过复制。

提示文案改为「已打开主题详情，加载几秒后点『免费试用』」。

## 十八、0.5.4-beta（versionCode 81）：交给主题商店支持免 Root

写 `Download/MCTGA/` 从 root `cp` 改成 MediaStore Downloads（`RELATIVE_PATH=Download/MCTGA/`，
先 `IS_PENDING=1` 再清零），API 29+ 不需要存储权限；同名同大小复用；有 Root 时补 `chmod 0644`。
安装按钮不再随 Root 隐藏，`/data/theme` 手动写入仍留在高级且需要 Root。
